# M7 — Active Implementation Record

M7 began from canonical `main` at
`14da51f530bd859afebf1ce2d9ed0348a8832f33`, after M6A acceptance and the
fail-closed M8B/M8C integration were published.

The platform-neutral managed-service, installation, bootstrap, doctor, manual
fallback and qualification-harness foundation is implemented and black-box
verified from a clean installed wheel.

The Product Owner resolved the qualification matrix on 2026-08-28. Core GA is
qualified on three independent Windows 11 24H2 or 25H2 x64 clean-VM cells: Codex-only
for J01 and J16, Claude-only for J02 and J16, and no-provider for J10. Provider
coexistence is not required by M7 and no result may be inferred across cells.
The Product Owner explicitly added 25H2 eligibility on 2026-08-28 and then
designated it the preferred newer baseline; the active qualification environment
therefore uses 25H2.

M7 is now `BLOCKED_EXTERNAL_PREREQUISITE`, not `ACCEPTED`. The Windows 11 per-user Task Scheduler
adapter and public distribution lifecycle are implemented and source-qualified,
but they are not yet qualified from the single provenance-bound shipping
candidate on the three clean-VM cells. The approved per-user service model uses
`InteractiveToken`; each cell therefore records an interactive user logon before
service activation and makes no pre-logon headless-start claim. Developer-machine,
combined-provider and source-tree evidence remain ineligible.

The VM104 qualification base was generalized and independently first-booted on
2026-08-29. The pre-generalization snapshot is explicitly invalid for M7 evidence
because it duplicated the qualification client's Machine SID. The current reset
source for cell execution is `m7-qualified-25h2-x64-cell-base-v8`, derived through
`m7-generalized-25h2-x64-base` and the retained predecessor resets, on
Windows 11 Pro 25H2 build `26200.9168`. V3 exposed and preserves the rejected
native Task Scheduler XML stream-encoding regression; V4 exposed and preserves
the rejected Task Scheduler registration-URI normalization regression. V5 is
invalid because it booted into Automatic Repair after a hard stop. V6 was
created from the boot-verified v4 lineage after a graceful Windows shutdown;
its native run exposed and preserves the rejected Task Scheduler logon-identity
normalization regression. V7 was created from v6 after a graceful Windows
shutdown and was boot-verified; its native run exposed and preserves the
rejected distribution-doctor regression for an uncreated nested Project path.
V8 was created from v7 after a graceful Windows shutdown, was boot-verified,
and contains the repaired, release-finalized native candidate built from
`965f46f9be66b891e35c19ad6c0144e448486a67`.
The earlier reset candidates cannot supply current cell evidence. The
post-generalization SID is distinct, RDP reached the final desktop,
Codex/Claude/Node remain absent,
and transient AutoLogon, unattend, RDP credentials and update payloads were
removed. During the native J10 attempt, Microsoft Defender event 1116 detected
`Behavior:Win32/Execution.A!ml` (threat ID `2147735815`) and event 1117
successfully quarantined the staged executable, installed executable, running
managed service and its Task Scheduler persistence objects. Task Scheduler event
141 independently records `SYSTEM` deleting the managed-service task at the same
boundary. No Defender exclusion, disablement or quarantine restore is eligible
for clean-VM evidence.

Candidate `5a331c3daf32601ad2af2ba870f9c9686ad4d44c5ec1082460abe4a016779f00`
and its candidate-bound V8 attestation are therefore rejected for M7 cell
qualification. J01, J02, J10 and J16 remain unclaimed. Resumption requires a
trusted Authenticode-signed candidate or Microsoft false-positive clearance and
a new provenance-bound clean snapshot. If that cannot preserve the frozen
PyInstaller baseline, the packaging ADR revisit trigger requires Architect
approval before implementation changes.
