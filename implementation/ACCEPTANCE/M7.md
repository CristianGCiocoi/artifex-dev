## VM105 standalone Codex outcome — blocked

VM105 was created from the generalized Windows 11 25H2 base as an independent
Codex-only cell with a distinct SID. The exact V10 candidate was staged before
the immutable `m7-qualified-25h2-x64-codex-cell-v10` snapshot; Codex, Claude,
Node, ARTIFEX and source checkout were absent at that boundary. After the human
established the required interactive logon, official Codex CLI `0.150.1` was
installed and authenticated. Its bounded authentication probe passed.

The first non-resumed public shipping journey installed the exact V10 candidate,
persisted provider setup and crossed the managed-service restart boundary. The
real `EXECUTION_IMPLEMENTER` Attempt then returned a structured durable
`BLOCKED` result, created no owned artifact, and recorded validation evidence
with `passed=false`. No Acceptance decision exists. The runner's immediate
capture reported a transient `runtime.status` JSON failure, but a subsequent
read-only public frontend reconnection returned the same durable Run and exposed
the underlying provider outcome. Both observations are bound in
`EVIDENCE/M7-WINDOWS-CODEX-VM105-V10-DURABLE-BLOCKED.json`.

The later read-only RunStore and Codex sandbox diagnostics corrected the original
external-provider classification. The durable provider message had not been
persisted by ARTIFEX, but the native sandbox log showed the exact failing operation:
creation of `deliverables` was denied inside the managed Execution Workspace under
`AppData\Local\ARTIFEX\runtime\workspaces`. A bounded diagnostic then reproduced
the same `BLOCKED` result and exact access-denied message in a fresh child of that
root. The same Codex executable and sandbox produced the exact requested artifact
in a fresh AppData workspace outside the private RunStore state tree. These two
diagnostics are retained in
`EVIDENCE/M7-WINDOWS-CODEX-VM105-PATH-DIAGNOSTIC-1.json` and
`EVIDENCE/M7-WINDOWS-CODEX-VM105-PROVIDER-ROOT-DIAGNOSTIC-2.json`; both are marked
diagnostic-only and cannot satisfy J01 or J16.

The defect is therefore an M7 shipping-composition issue: on Windows, the V10
managed service placed provider workspaces beneath the deliberately private
RunStore DACL. The remediation keeps RunStore, fencing and transport credentials
inside the private state root while giving the managed Execution Workspace a
deterministic sibling root. Workspace ownership, envelope checks, isolated clone,
Acceptance Authority and Project Authority boundaries remain unchanged. The M7
harness now consumes the workspace authority reported by the shipping managed
service and fails closed if Windows provider workspaces remain nested beneath the
private state tree.

J01 is `ACTIVE` in implementation remediation; J16 remains `ACTIVE` and unclaimed.
V10's J10 pass and Codex blocked result remain immutable provenance, but a new
candidate must requalify all mandatory M7 cells before acceptance. No diagnostic,
retry, authentication result, interaction result or other-provider success is
selected as a substitute for the clean-cell journeys.
